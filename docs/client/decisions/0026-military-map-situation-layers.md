# 0026 — Military and analysis map situation layers

Date: 2026-09-26. Status: implemented.

## Decision

Keep strategic military context on the existing World map and put its preferences in the existing Layers menu under a Military heading. **Show units** is enabled by default and can hide every unit marker and its map hit target while retaining independent battle and defence layers. Visible stack markers always separate persistent Guard divisions from other active divisions with a shield badge. Each badge is an independent hit target: the shield selects Guard divisions for Release/Disband actions, while the ordinary badge selects non-Guard active divisions for orders. The optional **Show unit details** preference adds the compact order-aware `DEF` total and a composition row by unit type, while close zoom keeps the existing individual miniatures. These are presentation preferences stored with the per-game World view; they do not alter orders or authoritative game data.

The force-selection panel keeps a visible compact filter strip for Idle, Guard and all five unit types. A normal click includes that value; Shift-click excludes it; repeating the same action clears it. Values within one category combine as OR and state/type categories combine as AND. Select all applies only to shown units. Changing a filter removes newly hidden units from the current selection so an order cannot silently include invisible divisions. Included and excluded states use distinct accent/danger treatments plus text/ARIA state; the full interaction is stated below the controls.

The optional **Show last-turn battles** preference draws every structured battle location from public current-turn News. Multiple battles on one territory aggregate into one marker. Exact attacker and defender formation-loss totals are added only when the current nation has a participant battle log for that battle. Spectators and uninvolved nations see the public location/outcome marker without private casualty numbers.

The saved **Analysis overlay** selector permits one quantitative heat map at a time: none, defence potential, population density, resource production or loyalty. All views share the continuous exposed-red through amber/green to protected-teal gradient, compact legend and selected-territory value. Defence, population and production adapt their upper endpoint to the 90th percentile of their current positive values; zero stays at the exposed end and a mild logarithmic curve keeps early- and late-game differences visible without allowing one exceptional territory to flatten the map. Loyalty uses a fixed 0–100% scale because its absolute gameplay threshold matters.

**Defence potential** colours only the current nation's territories by their projected defence if that territory alone were attacked now. It adds confirmed staying, incoming and deploying defence to every reachable Guard unit whose remaining 75% response cost can be paid. A Guard already on the target is counted in base defence and omitted from the response contribution. The legend's full accessible description states that Guard units are reused across territory projections, so this is not a simultaneous-attack simulation. The Military force panel retains the exact base/Guard breakdown.

**Population density** uses known population divided by total territory area and may display owned or foreign inhabited territory. Unknown neutral population is omitted. **Resource production** displays one labor-produced resource at a time and is restricted to the current nation's territory; it sums the territory's current allocated facility output rather than its theoretical capacity. Recruitment pool is omitted because it is generated nationally from loyal population rather than territorial facilities. The selector receives every value from the confirmed World snapshot, so changing resources causes no read. **Loyalty** is also owner-only, uses current loyalty to the player's nation and states the existing greater-than-50% deployment requirement.

The saved **Mute foreign colours** preference places a neutral grey fill over foreign-owned territory while Military mode or an analysis overlay is active. Ownership borders retain their nation colours, and a hovered or selected foreign territory temporarily regains its fill colour. Selecting any analysis overlay enables this preference to keep foreign nation colours from competing with the gradient; the player may then switch it off independently. The quantitative overlay is drawn above that neutral base so world population values remain visible. Unclaimed and player-owned territory are unaffected.

`GameplayService.militaryHistory()` owns and coalesces the public/private read for the current game turn, fences it with the existing world generation and never calls the private endpoint for spectators. The map component owns only its saved military display preferences and projected markers. No new global store or polling loop is introduced.

`DefenseCoverageService` owns the private Guard reach and resource projection. It shares the exact route finder used by `GuardAllocator`, returns only the current nation's territories, performs no mutation and evaluates affordability independently for each hypothetical target. `GameplayService.defenseCoverage()` coalesces and generation-fences that read; the World feature combines it with the existing client-side order-aware base-defence projection. The result is discarded and re-read after any confirmed same-turn state change. Spectators are not offered the control.

Coverage performs one bounded reachability traversal per Guard and indexes every reachable owned territory from that result. It reads only resource budgets used by those Guard types. It does not repeat a route search for every Guard/territory pair or export unrelated budget sections.

## Data boundary

The additive battle migration stores nullable attacker/defender formation and division loss counts. New resolved battles populate them from the same `BattleLosses` objects used to apply casualties. Older battles and battles aborted before losses were calculated remain null. Only `ParticipantBattleLog` exports these fields; public News context remains limited to battle identity, participants, territory and outcome.

## Evidence and limits

Pure client tests cover Guard/non-Guard stack counts, unit composition, public marker aggregation, participant-only losses, defence projection, outlier-resistant scaling, continuous colour interpolation and foreign-fill exclusions. Focused Chromium coverage checks the grouped Layers controls, saved preferences, automatic foreign-colour muting, adaptive legend and selected-territory breakdown. The production build, generated API check, PHP syntax/contracts and isolated Guard engine pass. The Guard suite verifies reachable coverage, fuel affordability, bounded database reads, no local double count and no projection mutation. On the live 126-Guard/138-territory game, the optimized service retained the same 137 covered territories and 160–5,680 power range while reducing measured service time from 4.541 seconds and 186 queries to 0.255 seconds and 19 queries. These are local host measurements, not a latency guarantee. Existing battle rows cannot be retroactively given exact loss totals. Markers aggregate several battles at one territory and currently show attacker/defender formation totals rather than per-unit-type losses. The heat map excludes militia, unknown allied help and battle randomness; one Guard can appear as potential coverage for several territories because each is deliberately an independent scenario. The same colour represents a relative position in the current nation's current-turn distribution and can therefore change between turns even when one territory's absolute value does not. Full animated military history remains deferred.
